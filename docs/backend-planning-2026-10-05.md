# 本轮后端：情境、行动规划与时间消耗

本轮沿用 Capture → Parse → Life → Context → Now → Feedback 的闭环。模型负责从文字、图片、语音中提取有来源的生活事实；当下情境、硬约束、候选排序与行动状态由服务端代码和数据库处理。首页仍只给一个主要行动，必要时最多追问两题。

## 已实现的行为

### 有来源的事实与可重建投影

生活事实可保存耗时、费用、时间窗口、固定日程、地点、行动种类与目标阶段，同时保留原文证据。`USER_STATED` 与 `INFERRED` 分开；相对日期依据 Capture 的服务端时间和用户时区规范化。无法确定的时间、价格、坐标和条件保持未知。

耗时区分 `AVAILABLE` 与 `REQUIRED`，金额区分 `BUDGET` 与 `COST`，并区分 `CURRENT` 与 `OBJECT` 范围。“现在只有 20 分钟”可以成为当次情境，“旅行预算 3000 元”属于旅行目标。“我在广东，想去新疆旅行”保留广东为明确当前位置，不把新疆目的地变成出发地。

已有对象可通过 `PATCH /v1/life/:id` 修正并递增对象版本；后台补全检查版本，避免覆盖期间的修改，旧建议也不能启动更新后的事项。Now 每次最多为五个旧版本候选异步补全事实，同一对象修订不会重复入队；补全期间对象变化而取消后，新的修订可以重试。`POST /v1/life/:id/rebuild-facts` 也可将有来源的旧对象加入后台重建流程；这是异步处理，受理回执不代表已经解析完成。对象、事实和投影仍保留用户隔离及处理幂等。

### 服务端情境

`GET /v1/context` 返回当前用户的服务端时间、时区、本地日期与时钟、可用时长、预算、粗位置和忙闲情况。客户端不能指定服务器时钟、日历结果或记忆来源。

最近明确的当前位置可以作为 24 小时内的粗区域事实。用户明确保存的 HOME 与当前物理位置保持区分；HOME 不证明用户此刻在家，也不会静默长期保存精确 GPS。用户主动提供的精确坐标采用 GCJ02，观察时间必须有效，最多保留两小时。完整会话情境进入带清理期限的快照，长期会话摘要只保留粗区域。构建情境时清理本人过期快照，也清理超过 24 小时的旧精确快照。

最近两小时内的明确 `CURRENT` 可用时间和预算可补充当次情境，用户此次明确输入优先。模型只给上限的“只有 20 分钟／最多 20 元”也能被保留。目标预算不会混入当前预算；接受建议不会被当作已经消费。

### 时间确实随经过而减少

“现在只有 20 分钟”建立截止时间：Capture 服务端时间加 1200 秒。六分钟后再次请求建议，实际可用时间是 14 分钟；原来的 20 分钟仍用于展示原声明。`calendar.effectiveAvailableMinutes` 保留小数精度，用于行动秒数的硬过滤，避免四舍五入多给时间。

`calendar.availableUntil` 让会话恢复和无关追问保留原截止时间；用户重新明确回答可用时长时，才以这次服务端时间建立新窗口。同一输入产生多个可用时间事实时取最紧限制，较新的明确声明替换旧声明，不会重复扣减。

明确日程及已接受行动限制当前空闲窗口。未来固定事件的开始时间可以限制空闲时长；缺少结束时间时不会捏造全天占用。精确的“明天下午 3 点到 4 点有会议”可形成固定忙碌区间；宽泛的“明天下午”保留为窗口，不会被当成整个下午的固定会议。

### 单个可执行行动与必要追问

Now 先做时间、预算、日程、出门意愿等硬过滤，再排序。信息足够时直接推荐；只有候选接近，且某个缺失答案会改变首选时才提出自然问题。最多两题，一题解决就停止，问题与答案只属于该会话。会话隔离、答案选项校验、重复提交和过期检查保留在后端。

行动区分 `DO` 与 `PREPARE`。已知短行动可安排执行；旅行、长期目标或条件不足的目标可转成列日期、整理预算、核对路线等有边界的准备步骤。准备步骤明确使用规划估计，不等于目标本身的实际耗时。内容时长未知时，可以安排有边界的小段体验，不声称能够在该时段完成整本或整集。受当前截止时间限制的估计准备或体验时段留出 15 秒启动余量；已知完整行动的所需时长不会被压缩。

出门行动的时间需要包括活动、去程与返程。只有当前起点、目标坐标和未过期的双向路线都能匹配，才使用路线作为核验依据。交通核验不证明营业、预约或入场条件；未接通的条件不会被写成已核实。

### 内部开始、完成与取消

推荐计划带有开始、结束、总秒数及依据。`POST /v1/now/sessions/:id/feedback` 的 `ACCEPT`／`EXECUTE` 使用真实反馈服务端时间开始占用，并在开始前重新检查当前日程和剩余时间。数据库按用户串行化开始操作，防止两个并发行动同时消耗同一段时间。

`COMPLETE` 结束行动，`REJECT`／`DISMISS`／`SKIP` 取消占用。状态返回 `NOT_STARTED`、`ACTIVE`、`COMPLETED` 或 `CANCELLED`，已开始行动的 elapsed seconds 由服务器时钟计算。反馈事件和 Outbox 仍在同一事务提交，重复请求不重复启动。新录入和反馈优先于旧资料补全，两个 Worker 通道中保留一个处理新输入，避免后台修复占满处理资源。服务端计划元数据不接受客户端伪造。

`ACCEPT` 和 `EXECUTE` 都可以成为第一次开始信号；行动已开始后重复发送这些信号不会重设开始时间或延长占用结束时间。

## 腾讯位置服务配置与降级

`packages/integrations` 提供可替换的 `LocationProvider` 接口及腾讯 LBS REST adapter。服务端环境变量为：

- `TENCENT_LBS_KEY`：腾讯位置服务 WebService Key。
- `TENCENT_LBS_SECRET`：仅当 Key 启用 SN 校验时配置的签名密钥。

密钥只供 API 与 Worker 服务读取，不进入小程序、请求回包或仓库。变更环境变量后需重启两个服务。2026-10-05 已在测试服务器配置腾讯 WebService Key，采用授权 IP 校验。无配置时返回 `NOT_CONFIGURED` 并降级；`GET /v1/locations/status` 的 configured 表示服务配置存在，不代表腾讯当时的权限、额度或网络可用。配置与真实验收详见[腾讯地图接入说明](tencent-map-setup-2026-10-05.md)。

已实现地理编码及步行路线，固定使用腾讯 HTTPS 主机，拒绝重定向，限制超时且不输出含密钥的 URL。地理编码只接受达到可靠性和精度门槛的结果，不能把城市中心当成精确地址。最多处理五个目标，并发最多两条候选流程，整个批次最多两秒；去程和返程分别查询，不能用去程乘二冒充返程核验。路线最多有效五分钟，并受起点观察期限约束；没有长期 GPS 或路线缓存。

新输入解析后最多为五个明确目的地入队 `PLACE_LOCATION_ENRICH`，坐标解析不会阻塞 Capture READY。生活列表也可通过 `POST /v1/locations/refresh` 补全最多五个本人活动对象；命名地点没有坐标时显示“待定位”，普通无地点内容不提示坐标缺失。已核实的同地址坐标不重复查询，永久模糊结果在同一对象版本内复用。

目的地坐标保存到独立 `EXTERNAL_VERIFIED` facet，包含腾讯来源、查询地址、城市、观察时间和精度；只有同一地址、同一城市仍匹配才参与投影重建。修改目的地使旧坐标失效。Worker 使用所有者、对象版本、数据库修订及租约尝试校验，防止覆盖用户更改或跨用户写入。当前位置与 HOME 不参与目的地自动回填。

真实验证与可控接口测试分别记录；单元测试中的可控响应不等于腾讯服务已跑通。

官方配置与协议依据：[腾讯地理编码](https://lbs.qq.com/service/webService/webServiceGuide/address/Geocoder)、[腾讯路线规划](https://lbs.qq.com/service/webService/webServiceGuide/route/webServiceRoute)、[WebService Key 与签名规则](https://lbs.qq.com/faq/serverFaq/webServiceKey)。

## 尚未实现的外部能力

- 真实预订、购票、付款、订单履约及自动核销。
- 读取或写入手机系统日历、外部日历账户、日程同步或提醒推送。当前忙闲来自本产品已保存的明确事件与内部行动。
- 商家营业时间、活动入场条件、预约库存的外部查询。
- 公交、驾车、跨省交通价格与实时出行状态。当前 adapter 只实现步行路线。
- 自动推断用户当前位置或持续后台定位。

这些能力不能由模型回答、现有接口类型或准备行动代替实际接入。后续应新增对应 Provider，保存来源及有效期，并分别完成真实验收。

## 验证入口

修改共享包后先统一构建，再用独立随机 schema 运行测试：

```sh
pnpm build
TEST_DATABASE_URL=postgres://user:password@localhost:5432/life_test pnpm exec vitest run tests/unit/tencent-context.test.ts tests/integration/context.test.ts tests/unit/domain-planning.test.ts tests/integration/planning.test.ts
```

Context 测试覆盖用户隔离、服务端时钟、当前位置与目的地区分、精确位置期限、过期快照清理、CURRENT 上限与范围、时间消耗、会话截止时间恢复、精确与宽泛会议、旧未来事件被大量新事实覆盖时的召回，以及内部行动占用／终止。腾讯 adapter 测试使用可控传输，覆盖签名、超时、坐标校验、路线分钟到秒、双向路线及并发／数量限制。

2026-10-05，统一构建通过后，`tests/unit/tencent-context.test.ts` 与 `tests/integration/context.test.ts` 的 33 项测试全部通过，使用本地独立随机 schema。这项结果覆盖 Context 与地图 adapter 的测试边界，未调用真实腾讯地图。

同日完成地图配置后的完整本地测试为 285 项通过。22:47，`maps-20261005-2236` 发布的公开 API 与真实 Qwen、腾讯地图分别验收通过：具体地址持久化为外部核验坐标；去程和返程分别查询成功；“我现在在广东，只有20分钟，想去新疆旅行，旅行预算3000元”生成 5 分钟准备行动，完成准备后旅行目标仍保持 ACTIVE。地图验收采用公共地点周边合成起点，手机定位仍待设备验收。详细回执位置见腾讯地图接入说明。

真实模型、真实地图、本地 API／数据库、公开后端和微信真机是不同验收层。每项以对应运行结果为准。国内模型与多模态输入说明见[国内模型比较](domestic-model-comparison-2026-10-05.md)和[本轮接入说明](domestic-multimodal-2026-10-05.md)。
